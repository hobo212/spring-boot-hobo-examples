Claude Code Skill

ht-review

双路交叉代码 Review skill。Claude Code 与 Codex CLI 各自独立审查，交叉合并结果，内置静态分析前置、上线注意事项提取与历史持久化。

10审查维度
3支持语言
7执行阶段
∞历史记录
概述

工作原理

双路交叉是核心设计：Claude Code 和 Codex CLI 各自独立审查同一份代码，再交叉合并。两路都发现的问题标为「共识」（高置信度），单路发现的也保留。

在 AI review 之前，先通过工具链做确定性的编译和静态分析检查。编译失败立即终止，工具发现的问题作为确定性上下文注入 AI review，不再由 AI 重新判断。

[共识]
Claude + Codex 均发现
置信度：高
[Claude]
仅 Claude 发现
置信度：中
[Codex]
仅 Codex 发现
置信度：中
使用方式

命令参数

# 最常用：交互式询问代码范围
/ht-review

# 指定 diff 范围
/ht-review --diff HEAD~1
/ht-review --diff HEAD~3..HEAD

# branch 对比
/ht-review --branch feature/x..main

# 指定文件
/ht-review --files src/UserService.java,src/OrderService.java

# 注入需求文档（启用需求符合度检查）
/ht-review --diff HEAD~1 --req docs/需求/功能A.md

# 注入测试用例文档
/ht-review --diff HEAD~1 --testcase docs/tc.md

# 历史查询（立即退出，不触发 review）
/ht-review --list
/ht-review --list --filter blocker
/ht-review --show abc1234f

参数速查

参数类型说明
--diff <ref>代码范围如 HEAD~1、HEAD~3..HEAD
--branch <range>代码范围如 feature/x..main
--files <paths>代码范围逗号分隔文件路径
--req <path-or-url>文档注入.md/.txt/.pdf/.png/URL
--testcase <path-or-url>文档注入测试用例文档
--list查询列出最近 20 条历史（立即退出）
--list --filter <level>查询过滤 blocker/major/minor/info
--show <hash>查询按 hash 前缀展示历史报告（立即退出）
ℹ️
代码范围参数均可省略，省略时交互式询问，直接回车默认使用 diff HEAD~1。
执行流程

七个阶段

阶段 0配置加载
├─ 三层 YAML 配置（/etc / ~/.ht-review / 项目）
├─ 三层忽略规则（.ht-reviewignore）
└─ 项目 Review 指南（REVIEW.md，自由文本）
阶段 1参数解析
├─ --list / --show → 查询历史，立即退出
└─ 继续 review 流程
阶段 2上下文构建
├─ 2.1 获取代码变更（diff / branch / files 三模式）
├─ 2.2 应用忽略规则（glob + !pattern）
├─ 2.3 探索调用链（Grep 调用方 + 读测试文件）
├─ 2.4 读取文档（本地/PDF/图片/URL/需登录页面）
└─ 2.5 静态分析前置检查 ← 编译失败立即终止
阶段 3aClaude Code 独立 Review（10 个维度）
阶段 3bCodex CLI 独立 Review（并行执行）
阶段 4交叉合并
├─ issues 合并（共识判定 + 过滤 + 排序）
├─ test_case_coverage 合并
└─ deployment_checklist 合并
阶段 5输出 Markdown 报告
阶段 6持久化存储（写本地缓存 + 更新索引）
阶段 2.5

静态分析前置检查

在 AI review 之前，用工具链做确定性检查。编译必须通过，工具发现的问题注入上下文，AI 不重新判断，只补充说明和建议。

语言自动识别

特征文件识别语言
go.modGo
pom.xml / build.gradle / build.gradle.ktsJava
pyproject.toml / setup.py / requirements.txtPython
均不存在跳过，输出警告

支持 monorepo 多语言同时检测。

阶段 3a

审查维度（共 10 个）

#1 安全性 始终
SQL注入 · XSS · 硬编码密钥 · 鉴权缺失 · 弱加密 · 路径遍历
#2 性能 始终
N+1查询 · 全表扫描 · 大数据内存加载 · 缓存使用 · 同步阻塞IO
#3 功能正确性 始终
边界条件 · 异常处理 · 状态机完整性 · 资源关闭 · 事务边界
#4 代码质量 始终
命名规范 · 方法长度 · 重复代码 · 魔法数字 · 死代码 · 日志规范
#5 测试覆盖 始终
核心路径 · 异常路径 · 断言完整性 · Mock使用 · 边界值
#6 需求符合度 有 --req
实现是否覆盖需求所有功能点，行为是否与预期一致
#7 测试用例覆盖 有 --testcase
逐条核对用例是否有实现路径和对应测试方法
#8 自定义规则 有配置
逐条检查 .ht-review.yml 中 custom_rules 定义的规则
#9 项目 Review 指南 有 REVIEW.md
对照项目规范/架构约束/业务规则逐条检查，违反项 category = PROJECT_GUIDELINE
#10 上线注意事项 始终
主动提取 DB 变更、配置、上线顺序、缓存、MQ 等，输出 deployment_checklist
维度 #10

上线注意事项

从代码变更中主动识别，无需人工提示。输出到独立的 deployment_checklist（不混入 issues），按 timing 分组、risk 排序。

类型说明示例
DB_DDLDDL 变更，附 SQLALTER TABLE user ADD COLUMN tag VARCHAR(64)
DB_DML存量数据迁移/修复脚本UPDATE user SET status=1 WHERE ...
CONFIGApollo/Nacos/配置文件修改项新增 oss.host.prefix
FEATURE_FLAG新增开关、环境变量新增 enable_new_upload
DEPLOY_ORDER多服务上线顺序依赖需先上线 oss-service
CACHE缓存 key 结构变化需清理/预热key 格式从 user:id 改为 u:id
MQ新增 Topic/Consumer Group需提前创建 order-notify-topic
INFRA新增外部依赖需提前申请资源新增 Redis 实例
OTHER其他上线注意事项—

每条标注 timing（上线前 / 上线时 / 上线后）和 risk（HIGH / MEDIUM / LOW）。

阶段 4

交叉合并规则

同一问题判定（全部满足）

条件说明
同一文件file 字段相同
同一类别category 字段相同
行号邻近line_start 差值 ≤ 5，或行号区间有重叠；任一为 null 时仅凭前两条判断

排序规则

优先级规则
1severity 降序：BLOCKER → MAJOR → MINOR → INFO
2同 severity 内：[共识] 优先 → [Claude] → [Codex]
3同来源内：按文件名字母序，同文件按行号升序
配置体系

三层配置覆盖

最低优先/etc/ht-review/config.yml — 系统级
中等优先~/.ht-review/config.yml — 用户级
最高优先.ht-review.yml — 项目级（覆盖上层）
# .ht-review.yml — 项目级配置示例
dimensions:
  security: true
  performance: true
  correctness: true
  code_quality: true
  maintainability: true
  test_coverage: true
  requirement: true    # 有 --req 时生效
  test_case: true      # 有 --testcase 时生效
  deployment: true     # 上线注意事项，始终生效
min_severity: MAJOR       # 改为 MAJOR 可减少噪音
custom_rules:
  - "需要鉴权的接口 path 必须包含 /uauth/"
  - "Service 层禁止直接使用 HttpServletRequest"
codex:
  model: o3
report:
  show_info: true
  show_consensus_only: false
项目指南

REVIEW.md

在项目根目录放置 REVIEW.md，内容自动注入为第 9 个审查维度，违反项 category 标为 PROJECT_GUIDELINE。格式不限，自由文本 Markdown。

# 项目 Review 规范

## 接口规范
- 需要鉴权的接口，path 必须包含 `/uauth/`
- 对外网暴露的接口，path 必须包含 `/gwpub/`

## 架构约束
- Service 层禁止直接依赖 HttpServletRequest
- 跨模块调用必须通过 Feign Client，禁止直接注入对方 Repository

## 数据库规范
- 批量查询必须加分页，禁止无 LIMIT 的 SELECT *
- 新增表必须包含 create_time / update_time / is_deleted

## 日志规范
- 外部接口入参必须打印 INFO 日志
- catch 后必须打印完整 stack trace
忽略规则

.ht-reviewignore

三层叠加，支持 glob 模式。项目级 !pattern 可取消上层已定义的同名规则。

# .ht-reviewignore
**/generated/**
*.min.js
vendor/**
!src/vendor/custom.js   # 取消上层对此文件的忽略

阶段 6

本地持久化存储

.ht-review-cache/ ← 建议加入 .gitignore，不提交到仓库 index.json ← 统一索引，最多 100 条，供 --list 使用 abc1234f/ ← commit hash 前 8 位 report.md ← 完整 Markdown 报告（人类可读） result.json ← MERGED_ISSUES 结构化数据（程序可读） meta.json ← 时间/作者/文件列表/问题统计

存储规则

情况行为
同一 commit 重新 review覆盖，不重复
branch/files 模式目录名加后缀，如 abc1234f-branch
index.json 超过 100 条自动删除最旧记录
index.json 更新用 Python 脚本，无 jq 依赖
 
# 将缓存目录加入 .gitignore
echo '.ht-review-cache/' >> .gitignore
历史查询

--list / --show

查询命令立即退出，不触发 review 流程。

# 列出最近 20 条，按时间降序
/ht-review --list

# 只看有 BLOCKER 的记录
/ht-review --list --filter blocker

# 按 hash 前缀查看完整报告（前缀匹配，4位以上即可）
